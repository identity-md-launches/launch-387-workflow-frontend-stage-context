## Accounting repairs to the bundled base

The derived hook still extends `lib/uniswap-hooks/src/general/LimitOrderHook.sol`. That file is locally modified. `patches/LimitOrderHook.patch` is a unified diff against the exact bundled template version; all other vendored Solidity files preserve their source bytes. The public order ABI and Place/Fill/Cancel/Withdraw event signatures remain unchanged.

1. **Last cancellation stranded already-collected fee claims.** Reproduction: two owners place at one tick, a buy partly crosses it, first owner cancels (collecting fees into claims for the remaining owner), then the last owner cancels. The original base zeroed order totals without burning/redeeming those claims. The regression failed with 31,207,270,889,505 wei of ETH claims still held. The cancellation callback now redeems previously stored claims as well as newly removed principal/fees for the final owner.
2. **Withdrawal subtracted a historical absolute checkpoint from a shrinking total.** Reproduction: accrue fees, cancel one owner, reverse the price, let that owner rejoin with a tiny amount, fill, then let the larger owner withdraw first. The original base panicked with arithmetic underflow when the tiny owner withdrew. Fee accounting now uses cumulative per-liquidity Q128 growth and per-owner checkpoints/credits independent of remaining totals. Fees collected during a new deposit are attributed before adding its liquidity, and an existing owner's top-up preserves earned credits. Principal is stored separately and paid pro rata.
3. **Rounding must leave no unreachable claims.** Principal, fee growth and owner credits round down. The last withdrawer receives remaining integer dust. For two owners who join together the pro-rata regression allows at most two wei difference from a single combined division because principal and fees round separately. Exact aggregate payouts must equal both currency claim totals, including through repeated top-ups, cancellations, reversals and either withdrawal order. A non-final cancellation reallocates the owner's accrued fee credits and freshly collected fees to remaining liquidity; a final cancellation releases all remaining claims.

The repair changes private storage layout and internal callback payloads. There is no proxy or migration path and no deployed storage to preserve in this assignment. Checked arithmetic protects liquidity totals. A fresh review should stress Q128 precision, extreme liquidity/fees, multiple pools sharing currencies, different owner orderings, donations, and adversarial transfer behavior. The intended TKPF contract is a conventional exact-transfer ERC20 without callbacks.

## Hook-specific defenses and residual risks

| Area | Implementation and evidence | Remaining review focus |
| --- | --- | --- |
| Native ETH entry | Both order entry points require native currency0, spacing 60 and this hook; ETH-selling orders always revert. Test forces ETH into hook first. | No alternative route may place ETH-side liquidity using another owner's funds. |
| Permissions / callback sender | Constructor validates exactly 0x1040; BaseHook's external wrappers and unlock callback enforce PoolManager-only. Tests use real CREATE2 plus direct refusal checks. | Compare creation/runtime artifacts and constructor arguments to manifest. |
| Partial versus full crossing | Base removes orders after range crossing; derived `_fillOrder` also checks actual sqrt price is at/below the lower bound before removal. | Boundary ticks, negative tick flooring, reversals, repeated swaps and multiple pools. |
| Claims / reentrancy | Proceeds use PoolManager ERC-6909 claims and pull withdrawal. Ownership is cleared before payout; manager unlock rejects nested accounting. Failed receivers roll back and retry. | Reentry during cancellation and withdrawals of other IDs; malicious unsupported ERC20 callbacks. |
| Gas griefing | Linear afterSwap loop remains. 100-step, 100/140/150/200-filled-range and 2,000-empty-step benchmarks document costs. | Gas limits of actual router/network; cheap dust-order spam; fragmentation of liquidity. |
| Manipulation and swap back | Regression fills an order, swaps back, opens a new ID and redeems unchanged old proceeds. Filled liquidity is removed, so reversal cannot undo that fill. | This does not prove manipulation unprofitable or protect against sandwiching/arbitrage. Orders accept range execution at manipulable spot prices. |
| Token policy | Fixed supply minted to deployer; transfer/allowance failures, supply conservation and no common admin/mint selectors tested. Runtime opcode scans cover both deployed contracts. | Rebuild reviewed code and compare source/ABI/runtime; scans are a floor, not a proof. |

The cached tick view is bookkeeping, not an oracle. Only placing users receive order ownership; swap hookData cannot authenticate users and is ignored. There is no fee recipient or reward path for a router to claim. Native pools with other tokens can attach the hook permissionlessly; operational interfaces must verify the exact accepted TKPF pool. Initialization and base bookkeeping are deliberately unrestricted so unrelated pools and one-sided seeding work.

No independent review, live Sepolia fork rehearsal, attestation, manifest validation or deployment is claimed by this contribution. Those service/reviewer outcomes must be recorded separately. Tests run against vendored real v4 contracts with local balances, never environment variables, RPC forks or a funded wallet.
